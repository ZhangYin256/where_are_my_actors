# 排练通知 QQ Bot 需求规格说明书（最终版）

版本：1.0  
日期：2026-11-07  
状态：已根据决策确认  
适用范围：排练通知 QQ Bot 的设计、开发、测试、验收、部署与维护

---

## 1. 项目概述

### 1.1 项目目标

开发一个基于 QQ 的排练通知机器人，用于剧组 / 表演团队发布、修改、重新发布、查询和提醒排练通知，解决以下问题：

1. 排练通知格式不统一；
2. 演员容易遗忘排练时间和地点；
3. 导演、副导演需要重复手动提醒；
4. 演员可能加入多个剧组，需要集中查看个人排练安排；
5. 需要支持多剧组、多群场景下的角色权限管理。

---

### 1.2 项目范围

本项目本期实现：

1. QQ 群内发布排练通知；
2. 解析通知中的时间、地点、人员、内容、备注等信息；
3. 导演、副导演、管理员修改排练通知；
4. 修改后手动重新发布；
5. 演员、副导演、导演、管理员查看本剧组排练通知；
6. 演员私聊查询本人在多个剧组中的排练安排；
7. 排练开始前自动提醒；
8. 角色权限管理；
9. 剧组配置管理；
10. 审计日志查看；
11. 基于 Docker 的部署方案。

本期不包含：

1. 请假审批；
2. 签到统计；
3. 自动排班；
4. 冲突检测；
5. 日历订阅；
6. 复杂 Web 管理后台；
7. 短信、邮件、飞书、钉钉等其他通知渠道。

---

## 2. 技术选型

根据决策，本项目采用以下技术栈：

| 模块 | 选型 | 说明 |
|---|---|---|
| QQ 协议端 | NapCat | 负责登录个人 QQ、收发消息、提供 OneBot 接口 |
| 机器人应用框架 | NoneBot2 | 负责命令解析、业务逻辑、权限校验、定时任务 |
| 数据库 | SQLite | 轻量、单文件、适合剧组规模 |
| 定时任务 | APScheduler 或 NoneBot2 定时插件 | 支持持久化任务，重启后恢复 |
| 部署方式 | Docker 优先，也支持本地进程 | 适合常开个人电脑 / 服务器 |
| 运行平台 | Windows、Ubuntu、macOS | 至少保证主流平台可运行 |
| QQ 账号 | 专用个人 QQ 号 | 降低主账号风控风险 |

---

### 2.1 架构说明

系统整体架构如下：

```text
QQ 用户 / QQ 群
      ↓
NapCat 协议端
      ↓ OneBot 11 协议
NoneBot2 应用端
      ↓
SQLite 数据库
      ↓
定时提醒任务
```

NapCat 负责个人 QQ 登录和消息收发。  
NoneBot2 负责业务处理，包括：

1. 命令识别；
2. 权限校验；
3. 文本解析；
4. 时间解析；
5. 人员匹配；
6. 数据库读写；
7. 提醒任务调度；
8. 审计日志记录。

---

### 2.2 部署原则

1. 使用专用个人 QQ 号作为机器人账号；
2. 机器人账号应常开；
3. 优先使用 Docker Compose 部署；
4. 数据文件持久化保存；
5. 时区默认使用 `Asia/Shanghai`；
6. NapCat 登录会话需要持久化，避免频繁重新登录；
7. SQLite 数据文件需要支持备份。

---

## 3. 核心业务概念

### 3.1 剧组

一个剧组对应一个 QQ 群。

规则：

1. 一个 QQ 群只能绑定一个剧组；
2. 不存在一个 QQ 群内多个剧组的场景；
3. 同一个导演 / 副导演可以管理多个剧组，即其 QQ 号可以存在于多个剧组群中；
4. 每次排练的参与人员可以不同，不要求固定演员名单。

---

### 3.2 排练通知

每次排练通知包含以下信息：

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| 标题 | 固定 | 固定为 `#排练通知` |
| 时间 | 必填 | 支持模糊时间解析 |
| 地点 | 可空 | 可为“暂无”，空值不显示 |
| 人员 | 必填 | 支持 @群成员、文本人员、@全体成员 |
| 内容 | 可空 | 可为“暂无”，空值不显示 |
| 备注 | 可空 | 补充说明 |
| 提醒 | 可选 | 默认使用剧组配置 |
| 通知范围 | 可选 | 可包含 @全体成员 |

---

### 3.3 通知标题

正式发布的排练通知标题固定为：

```text
#排练通知
```

规则：

1. 所有正式群内通知首行标题固定为 `#排练通知`；
2. 不支持自定义通知标题；
3. 更新重发时标题仍为 `#排练通知`，可在正文中标注“已更新”；
4. 系统命令可支持 `#发布排练`，同时可提供别名 `#排练通知` 作为发布命令别名，但正式消息标题仍固定为 `#排练通知`。

## 4. 用户角色与权限

### 4.1 角色定义

| 副导演 | 剧组协助管理角色 |
| 演员 | 普通参与人员 |

补充规则：

1. 管理员、导演、副导演可以同时作为演员参与排练；
2. 一个 QQ 号可以在多个剧组中拥有不同角色；
3. 一个群只对应一个剧组；
4. QQ 群主和 QQ 群管理员自动成为该剧组的导演。

### 4.3 权限规则细化

#### 4.3.1 管理员

管理员拥有最高权限，包括：

1. 设置 / 取消管理员；
2. 设置 / 取消导演；
3. 设置 / 取消副导演；
4. 管理所有剧组；
5. 管理所有排练通知；
6. 管理所有演员；
7. 修改全局配置；
8. 查看审计日志；
9. 解绑剧组；
10. 物理删除数据。

---

#### 4.3.2 导演

导演拥有本剧组管理权限，包括：

1. 发布、修改、重新发布、取消、删除排练通知；
2. 添加、移除、编辑演员；
3. 配置提醒；
4. 配置是否私聊提醒；
5. 配置模糊时间晚上阈值；
6. 授权 / 取消副导演；
7. 查看审计日志。

限制：

1. 导演不能授权 / 取消导演；
2. 导演不能授权 / 取消管理员；
3. 导演不能修改全局配置；
4. 导演不能解绑剧组。

---

#### 4.3.3 副导演

副导演拥有本剧组部分管理权限，包括：

1. 发布、修改、重新发布、取消、删除排练通知；
2. 添加、移除、编辑演员；
3. 配置提醒；
4. 配置是否私聊提醒；
5. 配置模糊时间晚上阈值；
6. 查看审计日志。

限制：

1. 副导演不能授权 / 取消任何角色；
2. 副导演不能修改全局配置；
3. 副导演不能解绑剧组。

---

#### 4.3.4 演员

演员权限包括：

1. 接收排练通知；
2. 接收排练提醒；
3. 查看本剧组所有排练通知；
4. 查看本剧组历史排练；
5. 按周查看本剧组排练；
6. 私聊查询本人在多个剧组中的排练安排。

限制：

1. 演员不能发布、修改、删除通知；
2. 演员不能管理角色；
3. 演员不能查看审计日志；
4. 演员不能修改配置。

---

### 4.4 群主和群管理员自动成为导演

规则：

1. QQ 群主自动成为该剧组导演；
2. QQ 群管理员自动成为该剧组导演；
3. 自动导演角色由系统同步维护；
4. 当某用户不再是群主或群管理员时，系统自动撤销其由群身份获得的导演角色；
5. 如果该用户另外被手动授权为副导演、导演或管理员，则手动角色不受自动撤销影响；
6. 系统角色与群身份角色应分开记录，避免误删手动授权。

以下需求编号用于开发、测试和验收。

优先级定义：

| 优先级 | 含义 |

| P0 | 必须实现 |

## 5.1 FR-01 剧组绑定

优先级：P0

### 功能描述

系统支持将一个 QQ 群绑定为一个剧组。

### 规则

1. 一个 QQ 群只能绑定一个剧组；
2. 一个剧组只能绑定一个 QQ 群；
3. 管理员可以在群内初始化剧组；
4. 剧组信息包括：
   - 剧组 ID；
   - 剧组名称；
   - 绑定群号；
   - 时区；
   - 默认提醒时间；
   - 模糊时间晚上阈值；
   - 是否私聊提醒；
   - 是否显示备注标签；
   - 创建时间；
   - 状态。
5. 管理员可以修改剧组名称；
6. 管理员可以解绑剧组；
7. 解绑后停止该剧组提醒，但历史数据保留。

### 命令示例

```text
#初始化剧组 某某剧组
#剧组信息
#修改剧组名称 某某剧组
#解绑剧组
```

---

## 5.2 FR-02 角色授权

优先级：P0

### 功能描述

系统支持管理员、导演、副导演的授权和取消。

### 规则

1. 初始管理员通过配置文件指定；
2. 管理员可以授权 / 取消管理员；
3. 管理员可以授权 / 取消导演；
4. 导演可以授权 / 取消副导演；
5. 导演不能授权 / 取消导演；
6. 副导演不能授权 / 取消任何角色；
7. 群主、QQ 群管理员自动成为导演；
8. 手动授权角色与群身份自动角色分开记录；
9. 所有授权和取消操作写入审计日志。

### 命令示例

```text
#授权导演 @张三
#取消导演 @张三

#授权副导演 @李四
#取消副导演 @李四

#授权管理员 123456789
#取消管理员 123456789
```

---

## 5.3 FR-03 演员管理

优先级：P0

### 功能描述

导演、副导演、管理员可以维护剧组演员信息。

### 规则

1. 演员可以是群成员，也可以是文本人员；
2. 文本人员用于表示无法精确 @ 的对象，例如“制作组”；
3. 支持添加演员；
4. 支持移除演员；
5. 支持查看演员列表；
6. 支持为演员设置别名；
7. 支持为演员设置备注标签；
8. 备注标签默认不在通知中显示；
9. 移除演员不删除历史排练参与记录；
10. 每次排练参与人员可以不同于演员表。

### 命令示例

```text
#添加演员 @张三
#添加演员 制作组
#移除演员 @张三
#演员列表
#演员别名 @张三 小张
#演员标签 @张三 湖区
```

## 5.4 FR-04 发布排练通知

优先级：P0

### 功能描述

导演、副导演、管理员可以发布排练通知。

### 发布入口

1. 在剧组群内发布；
2. 私聊 Bot 发布，需指定剧组；若操作者仅管理一个剧组，可省略剧组。

### 命令

主命令：

```text
#发布排练
```

别名：

```text
#排练通知
```

---

### 发布格式

支持多行格式：

```text
#发布排练
时间=周五7~10
地点=一排
人员=@冯然 @关静一 制作组
内容=
1. 福临门开场和声
2. 一念一宇宙
备注=其他演员可以来自由练习
提醒=30
通知范围=全体成员
```

也支持：

```text
时间：周五7~10
地点: 一排
人员=@冯然 @关静一
```

字段分隔符支持：

```text
=
：
:
```

即以下写法等价：

```text
地点=一排
地点：一排
地点:一排
```

---

### 固定标题

正式群消息标题固定为：

```text
#排练通知
```

示例：

```text
#排练通知
时间：11月13日 周五 19:00-22:00
地点：一排
人员：@冯然 @关静一 制作组
内容：
1. 福临门开场和声
2. 一念一宇宙
备注：其他演员可以来自由练习
```

---

### 空值处理

1. 地点可以暂无；
2. 内容可以暂无；
3. 备注可以暂无；
4. 值为空、`暂无`、`无`、`-` 时视为空；
5. 空值字段在正式通知和提醒中默认不显示；
6. 不显示标签，默认不展示备注标签。

示例：

```text
地点=暂无
内容=暂无
```

 equivalent to not providing these fields.

---

### 预览

发布前必须支持预览。

流程：

1. 操作者发送发布内容；
2. 系统解析字段；
3. 系统生成预览；
4. 操作者确认后正式发送；
5. 操作者取消则不发送。

预览示例：

```text
【发布预览】
标题：#排练通知
时间：2026-11-13 周五 19:00-22:00
地点：一排
人员：@冯然 @关静一 制作组
内容：
1. 福临门开场和声
2. 一念一宇宙
备注：其他演员可以来自由练习
提醒：提前30分钟

如确认发布，请发送：
#确认发布 P001

取消请发送：
#取消发布 P001
```

---

### @全体成员

1. 如果通知中包含 `@全体成员`，系统需要识别；
2. 不在人员字段中的 `@全体成员` 仅表示提醒全群，不参与人员匹配；
3. 人员字段中的 `@全体成员` 表示参与对象为全体成员；
4. 若机器人是群管理员，可发送真正的 `@全体成员`；
5. 若机器人不是群管理员，不支持真正 `@全体成员`；
6. 若人员包含 `@全体成员` 且机器人不是群管理员，则降级为逐个 @ 所有应通知成员；
7. 逐个 @ 时可根据配置选择目标范围；
8. 为避免风控，逐个 @ 可分段发送，并加入发送间隔。

---

## 5.5 FR-05 时间解析

优先级：P0

### 功能描述

系统需要解析排练时间，并支持模糊时间。

### 基本要求

1. 不要求输入年份；
2. 正式通知默认不显示年份；
3. 系统内部必须存储完整日期时间；
4. 时区默认 `Asia/Shanghai`；
5. 时间解析结果必须在预览中明确展示；
6. 若解析结果存在自动顺延，需要提示。

---

### 支持的日期表达

1. `今天`
2. `明天`
3. `后天`
4. `周一` 至 `周日`
5. `星期一` 至 `星期日`
6. `礼拜一` 至 `礼拜天`
7. `10.21`
8. `10/21`
9. `10月21日`

---

### 支持的时间表达

1. `晚上8:30~10:00`
2. `晚8:30~10:00`
3. `下午2点~4点`
4. `上午9点~11点`
5. `19:30-21:00`
6. `7~10`
7. `周五7~10`
8. `周一晚8:30~10:00`

---

### 模糊时间规则

#### 规则 1：周几 + 时间

示例：

```text
周一晚8:30~10:00
```

如果在周一早上发布：

- 系统识别为当天晚上 20:30-22:00。

如果在周一晚上开始时间之后发布：

- 系统识别为下周一 20:30-22:00；
- 预览中提示“开始时间已过，按下一周处理”。

示例：

```text
周五7~10
```

如果在周六发布：

- 系统识别为下一周周五；
- 时间按晚上解析，即 19:00-22:00。

---

#### 规则 2：只写小时范围

示例：

```text
7~10
```

系统应支持解析为：

```text
19:00-22:00
```

规则：

1. 当未指定上午 / 下午 / 晚上时；
2. 若开始小时小于“晚上判定阈值”，默认按晚上处理；
3. 晚上判定阈值支持配置；
4. 默认阈值：`9`；
5. 即开始时间小于 9 点时，默认视为晚上；
6. 结束时间默认跟随开始时间按时段解释；
7. 如果结束时间小于开始时间，则视为跨天。

示例：

| 输入 | 默认解析 |
|---|---|
| `7~10` | 19:00-22:00 |
| `8~11` | 20:00-23:00 |
| `8~1` | 20:00-次日01:00 |
| `晚8:30~10:00` | 20:30-22:00 |
| `下午2点~4点` | 14:00-16:00 |

---

#### 规则 3：晚上阈值可配置

配置项：

```text
ambiguous_evening_threshold
```

默认值：

```text
9
```

说明：

- 当开始小时小于该阈值时，默认按晚上解释；
- 若希望 `9~11` 也默认按晚上解释，可将阈值设置为 `10`；
- 该配置支持剧组级别设置。

---

#### 规则 4：无年份日期

示例：

```text
10.21 下午2点~4点
```

规则：

1. 如果日期在今天之后，使用今年；
2. 如果日期是今天，使用今天；
3. 如果日期在今年今天之前，自动按下一年处理；
4. 预览中必须明确提示“该日期已过，已按下一年处理”；
5. 正式通知默认不显示年份；
6. 若目标日期跨到下一年，可显示为“明年10月21日”。

---

#### 规则 5：开始时间不足

如果发布通知时距离开始时间不足配置的提醒时间：

1. 仍允许发布通知；
2. 不再补发已经错过的提醒；
3. 如果尚未开始，可以只发布通知；
4. 如果开始时间已过，预览中提示“开始时间已过，将不会发送提醒”。

---

## 5.6 FR-06 人员解析

优先级：P0

### 功能描述

系统需要解析通知中的人员，并尽可能对应到群内成员。

### @人员

1. 优先识别 QQ 消息中的 @ 成员；
2. 已识别 @ 成员可作为精确提醒对象；
3. 通知中需要 @ 对应人物；
4. 重复 @ 需要去重。

---

### 文本人员

允许使用无法对应群成员的文本人员，例如：

```text
制作组
```

规则：

1. 允许发布；
2. 系统必须明确提示该人员不能作为精确提醒对象；
3. 文本人员不会被 @；
4. 文本人员不会接收私聊提醒；
5. 文本人员仅作为通知展示对象。

预览提示示例：

```text
以下人员无法精确匹配到群成员，将仅作为文本展示，不能 @ 或私聊提醒：
- 制作组
```

---

### 备注标签

原始格式中类似以下内容：

```text
湖区@李柃锋
牌区@舒航
```

系统将“湖区”“牌区”等解析为备注标签。

规则：

1. 备注标签只用于标记人员；
2. 备注标签不参与人员匹配；
3. 备注标签默认不在通知中显示；
4. 可以通过配置开启显示备注标签；
5. 备注标签可保存到人员参与记录中。

支持的标签写法包括：

```text
湖区@张三
@张三(湖区)
@张三[湖区]
```

默认显示效果：

```text
@张三
```

开启标签显示后可选效果：

```text
@张三（湖区）
```

---

### @全体成员

1. 不在人员字段中的 `@全体成员` 只是为了提醒全群，不参与人员匹配；
2. 人员字段中的 `@全体成员` 表示参与对象为全体；
3. 系统应识别真实 `at_all` 消息段，也应识别文本 `@全体成员`；
4. 机器人是群管理员时可发送真正 `@全体成员`；
5. 机器人不是群管理员时不能发送真正 `@全体成员`；
6. 若人员包含 `@全体成员`，降级为逐个 @ 所有应通知成员；
7. 逐个 @ 的目标范围可配置，默认为全体应通知成员。

3. 操作者提交修改内容；
4. 系统解析修改内容；
5. 系统生成修改后预览；

7. 修改后不自动重新发布；
8. 操作者需要手动执行重新发布命令。

修改内容之后、重新发布之前必须支持预览。

```text
人员：@张三 @李四

取消请发送：
#取消修改 M001
```

保存后提示：

```text
修改已保存。
如需在群内重新发布，请发送：
#排练重发 3
```

---

### 重新发布

重新发布必须手动执行。

命令：

```text
#排练重发 编号
```

规则：

1. 重发前支持预览；
2. 确认后发送；
3. 正式消息标题仍为 `#排练通知`；
4. 正文可提示“以下为更新后的排练通知”；
5. 重发后提醒任务同步更新；
6. 不自动重发。

---

### 历史版本

根据决策：

1. 不保留排练通知历史版本；
2. 修改采用当前值覆盖；
3. 审计日志可记录修改动作和摘要；
4. 不要求保存完整历史快照。

## 5.10 FR-10 排练前提醒

优先级：P0

### 功能描述

系统需要在排练开始前发送提醒。

1. 默认提前 30 分钟提醒；
2. 默认提醒时间可按剧组配置；
3. 单条排练可单独设置提醒；
4. 支持多个提醒时间；
5. 支持关闭提醒。

命令示例：

```text

```

---

### 提醒消息标题

提醒消息标题建议为：

```text
#排练提醒
```

示例：

```text

还有30分钟开始

地点：一排
内容：

2. 一念一宇宙

@冯然 @关静一
```

---

### 空字段处理

1. 地点为空时不显示地点；
2. 内容为空时不显示内容；
3. 备注为空时不显示备注；
4. 标签默认不显示。

---

### 提醒对象

1. 已匹配 QQ 成员的参与人员可以被精确 @；
2. 文本人员不能被 @；
3. 文本人员不能接收私聊提醒；
4. 如通知包含 `@全体成员` 且机器人是群管理员，可 @全体成员；
5. 如机器人不是群管理员，则降级为逐个 @ 所有应通知成员；
6. 逐个 @ 可分段发送。

---

### 私聊提醒

是否私聊演员支持配置，默认不支持。

配置项：

```text
private_remind
```

默认值：

```text
false
```

规则：

1. 默认只在群内提醒；
2. 如果开启私聊提醒，则同时向已匹配 QQ 成员的参与人员发送私聊提醒；
3. 私聊提醒需要显示剧组名称；
4. 文本人员不私聊；
5. 私聊提醒失败写入日志。

私聊提醒示例：

```text
【排练提醒】剧组A
还有30分钟开始
时间：今天 19:00-22:00
地点：一排
内容：福临门合排
```

---

### 开始时间不足

如果发布时距离开始时间不足提醒时间：

1. 只发布排练通知；
2. 不补发已错过的提醒；
3. 如果当前时间尚未开始但未达提醒时间，可只等待剩余提醒；
4. 如果当前时间已开始或已过，不发送提醒。

---

### 提醒任务可靠性

1. 提醒任务必须持久化；
2. 机器人重启后未发送提醒应恢复；
3. 同一提醒不得重复发送；
4. 修改排练时间后提醒任务同步更新；
5. 取消或删除排练后提醒任务停止；
6. 发送失败可重试；
7. 重试次数建议不超过 3 次；
8. 失败原因写入日志。

3. Debian 12 及以上；
4. macOS 13 及以上；

推荐部署方式：

## 9.2 性能需求

| 指标 | 目标 |
|---|---|
| 命令响应时间 | < 2 秒 |
| 发布解析时间 | < 3 秒 |
| 私聊查询响应 | < 2 秒 |

| 支持群成员数 | 500 人 / 群 |
| 支持剧组数 | 初期 10 个 |
| 支持未来排练记录 | 1000 条 |

## 9.3 可靠性需求

1. NapCat 断线后应支持自动重连；
2. NoneBot2 重启后提醒任务应恢复；
3. SQLite 应启用 WAL 模式；
4. 提醒任务必须幂等；
5. 同一提醒不能重复发送；
6. 长消息应支持分段发送；
7. 消息发送失败应记录日志；
8. 可配置重试次数。

---

## 9.4 安全需求

1. 所有管理命令必须校验角色；
2. 演员不能执行管理命令；
3. 私聊查询只能查询本人数据；
4. 不应向普通用户泄露他人 QQ 号；
5. 审计日志仅副导演、导演、管理员可见；
6. 配置文件中的敏感信息不得公开；
7. 命令输入应防止注入；
8. 发送频率应受限，避免触发 QQ 风控。

## 9.5 可维护性需求

1. 命令解析、时间解析、权限校验、消息发送模块化；
2. 时间解析必须有单元测试；
3. 权限校验必须有测试用例；
4. 提供运行日志；
5. 提供错误提示；
6. 支持配置热更新或重启生效；
7. 数据库支持备份。

---

## 9.6 可用性需求

1. 中文提示；
2. 错误信息提供修正建议；
3. 发布模板清晰；
4. 时间解析结果必须预览；

# 10. 异常与边界处理

```text
时间无法识别，请使用类似格式：
周五7~10
周一晚8:30~10:00
明天下午2点~4点
```

## 10.2 人员无法匹配

提示：

```text
以下人员无法精确匹配到群成员，将仅作为文本展示，不能 @ 或私聊提醒：
- 制作组
```

发布者确认后仍可发布。

---

## 10.3 机器人不是群管理员

如果通知需要 @全体成员：

```text
当前机器人不是群管理员，无法发送 @全体成员。
系统将降级为逐个 @ 相关成员。
```

---

## 10.4 开始时间已过

提示：

```text
该排练开始时间已过，将不会发送提醒。
如仍需发布，请确认。
```

---

## 10.5 日期已过

如果无年份日期已过：

```text
该日期今年已过，系统已按下一年处理。
请在预览中确认时间。
```

---

## 10.6 周几时间已过

如果今天发布今天某时间，但开始时间已过：

```text
今天的该时间已过，系统已按下一周同一天处理。
请在预览中确认时间。
```

# 12. 验收标准

## 12.1 技术栈验收

1. 使用 NoneBot2 作为应用框架；
2. 使用 NapCat 作为 QQ 协议端；
3. 使用 SQLite 存储数据；
4. 可在 Windows、Ubuntu、macOS 上运行；
5. 可通过 Docker Compose 部署。

---

## 12.2 权限验收

1. 演员可以查看本剧组所有排练通知；
2. 副导演可以删除排练通知；
3. 副导演可以查看审计日志；
4. 导演可以授权副导演；
5. 导演不能授权导演；
6. 群主自动成为导演；
7. 群管理员自动成为导演；
8. 一个 QQ 号可以在多个剧组中担任导演或副导演。

---

## 12.3 发布验收

1. 正式发布标题为 `#排练通知`；
2. 支持 `=`、`：`、`:` 作为字段分隔符；
3. 地点和内容可以为空；
4. 空字段不显示；
5. 备注标签默认不显示；
6. 人员可包含文本人员；
7. 文本人员会提示不能精确提醒；
8. 已匹配人员会被 @；
9. 发布前支持预览；
10. 确认后才会正式发送。

---

## 12.4 时间解析验收

1. `周一晚8:30~10:00` 在周一早上发布，识别为当天 20:30-22:00；
2. `周五7~10` 在周六发布，识别为下一周周五 19:00-22:00；
3. `周五7~10` 默认解析为晚上；
4. 晚上判定阈值可配置；
5. 不需要输入年份；
6. 今年已过的月日日期按下一年处理，并在预览中提示；
7. 开始时间不足提醒时，只发布通知，不补发提醒。

---

## 12.5 修改与重发验收

1. 修改后支持预览；
2. 修改保存后不自动重发；
3. 手动执行 `#排练重发` 后群内发送更新通知；
4. 重发前支持预览；
5. 修改时间后提醒任务同步更新；
6. 不保留历史版本。

---

## 12.6 查询验收

1. 演员可在本剧组群内查看所有排练通知；
2. 演员可查看历史排练；
3. 演员可按周查看排练；
4. 演员私聊可查询本人多剧组安排；
5. 私聊结果按时间轴排列；
6. 私聊结果显示剧组名称。

---

## 12.7 提醒验收

1. 默认提前 30 分钟提醒；
2. 可配置多个提醒时间；
3. 可关闭提醒；
4. 地点 / 内容为空时提醒不显示；
5. 私聊提醒默认关闭；
6. 私聊提醒可配置开启；
7. 机器人重启后提醒任务恢复；
8. 同一提醒不重复发送。

---

## 12.8 @全体成员验收

1. 机器人是群管理员时可 @全体成员；
2. 机器人不是群管理员时不能 @全体成员；
3. 人员包含 @全体成员 时，非管理员场景下降级为逐个 @；
4. 不在人员中的 @全体成员 不参与人员匹配；
5. 降级逐个 @ 时能分段发送。

---

# 13. 风险与约束

## 13.1 协议风险

1. 个人 QQ 协议存在封号风险；
2. QQ 客户端更新可能导致 NapCat 不可用；
3. 应使用专用账号；
4. 应控制消息发送频率；
5. 应准备人工通知备用方案。

---

## 13.2 @全体成员风险

1. 非群管理员无法可靠 @全体成员；
2. 逐个 @ 所有成员可能触发风控；
3. 建议重要通知将机器人设为群管理员；
4. 可通过配置限制降级 @ 的范围。

---

## 13.3 时间解析风险

1. 模糊时间可能存在歧义；
2. 必须通过预览确认；
3. 跨年、跨周必须提示；
4. 晚上阈值需要根据剧组习惯配置。

---

## 13.4 SQLite 约束

1. SQLite 适合中小规模；
2. 不适合高并发写入；
3. 需要定期备份；
4. 如规模扩大，可迁移 PostgreSQL。

---
